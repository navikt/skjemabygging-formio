# New render compatibility notes

This note tracks the compatibility work needed to run the existing `packages/fyllut/cypress`
suites against the shared-frontend/new-render path without changing the tests.

For how new shared-frontend components should be written, see
`.github/skills/create-shared-frontend-component/SKILL.md`.

## Temporary legacy-compatibility shims

These changes exist mainly so legacy Cypress selectors and expectations continue
to work while we finish parity work. They should be reviewed again after the
full Cypress suite passes on the new renderer.

while we compare behavior.

## Remaining known parity gaps

These are the next areas to finish before removing temporary compatibility
support:

1. Any remaining parity gaps exposed by broader unchanged Cypress reruns outside the submission-type slices already covered here.
2. Select-like components are the one approved exception to strict legacy UI parity: keep native/Aksel interaction behavior and update Cypress expectations where old tests still assume react-select/ChoiceJS semantics. Current summary-page coverage uses `.select(...)` for that reason.
3. On the large `components` demo form in Electron, character-by-character typing in `Kontonummer` crashes the renderer. `summary-page.cy.ts` therefore uses a programmatic one-event input helper there, but that helper does not populate the summary row reliably, so the heavy summary-page spec currently skips the account-number summary assertion and relies on dedicated account-field specs for that coverage.

## Cleanup candidates after full Cypress parity

When the full existing Cypress suite passes on the new renderer, revisit these
first:

1. Remove the temporary `.form-group` class from `FormElementBox`.
2. Decide whether shared-frontend nav buttons should keep `role="link"` or go back to normal button semantics.
3. Re-check whether any legacy wording is still required on intro/panel navigation labels.
